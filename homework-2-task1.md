# Задание 1: Техники промптинга

## 🧭 Моя задача

Моя задача — составить план тестирования для фичи **push-уведомлений** в мобильном приложении.

## 📌 Почему выбрана эта задача

Я выбрала именно эту задачу, потому что на ней удобно показать влияние разных техник промптинга на качество ответа модели. В такой задаче важны сразу несколько аспектов:

- точность относительно бизнес-требований;
- полнота покрытия сценариев;
- удобный и воспроизводимый формат результата;
- учёт негативных сценариев и edge cases;
- различия между платформами Android и iOS.

Именно поэтому задача хорошо подходит для сравнения техник промптинга: она достаточно практическая, чтобы разница в качестве ответа была заметна, и достаточно сложная, чтобы общий ответ без дополнительных инструкций оказался неполным.

## 📘 Контекст

Есть мобильное приложение-мессенджер для **Android** и **iOS**.  
Нужно составить план тестирования для фичи push-уведомлений.

### Требования к фиче
- push приходит при новом личном сообщении;
- push приходит при упоминании пользователя в групповом чате;
- пользователь может отключить маркетинговые уведомления;
- пользователь может отключить все уведомления;
- при нажатии на push должен открываться соответствующий экран;
- в quiet hours с 23:00 до 08:00 не должны приходить маркетинговые уведомления;
- критичные уведомления должны приходить даже в quiet hours;
- поведение должно корректно работать на Android и iOS;
- если пользователь разлогинен, нажатие на push должно открыть экран логина, а после логина — целевой экран.

---

## 🔍 Почему здесь вообще важен качественный промпт

Если сформулировать запрос слишком общо, модель, скорее всего, даст поверхностный ответ вроде:

- проверить, что уведомления приходят;
- проверить, что уведомления можно отключить;
- проверить переход по нажатию;
- проверить работу на разных устройствах.

Такой ответ формально относится к теме, но его сложно использовать в реальной работе. В нём нет:

- привязки к конкретным требованиям;
- различия между типами уведомлений;
- проверки quiet hours;
- сценария для неавторизованного пользователя;
- платформенных особенностей;
- негативных сценариев и edge cases.

Именно здесь техники промптинга помогают не просто “сделать ответ длиннее”, а **сделать его точнее, структурнее и полезнее на практике**.

---

## 1. Grounding

Grounding снижает количество предположений в ответе модели, потому что задаёт конкретный предметный контекст, требования и ограничения. Вместо того чтобы “додумывать”, модель опирается на факты из запроса.

### Без техники (before)

**Промпт:**  
Составь план тестирования для фичи push-уведомлений в мобильном приложении.

**Ответ модели:**
- Проверить, что уведомления приходят.
- Проверить, что уведомления можно отключить.
- Проверить, что при нажатии открывается приложение.
- Проверить работу на разных устройствах.

### С техникой (after)

**Промпт:**  
Составь план тестирования для фичи push-уведомлений в мобильном приложении-мессенджере.  
Требования:
- push приходит при новом личном сообщении;
- push приходит при упоминании пользователя в групповом чате;
- пользователь может отключить маркетинговые уведомления;
- пользователь может отключить все уведомления;
- при нажатии на push должен открываться соответствующий экран;
- в quiet hours с 23:00 до 08:00 не должны приходить маркетинговые уведомления;
- критичные уведомления должны приходить даже в quiet hours;
- поведение должно корректно работать на Android и iOS;
- если пользователь разлогинен, нажатие на push должно открыть экран логина, а после логина — целевой экран.

Составь план тестирования в виде списка тестовых сценариев с ожидаемым результатом.

**Ответ модели:**
1. Проверить получение push при новом личном сообщении.  
   Ожидаемый результат: на устройство приходит push с текстом нового сообщения.
2. Проверить получение push при упоминании в групповом чате.  
   Ожидаемый результат: приходит push с указанием группы и факта упоминания.
3. Проверить отключение маркетинговых уведомлений.  
   Ожидаемый результат: маркетинговые push не приходят, системные и критичные приходят.
4. Проверить отключение всех уведомлений.  
   Ожидаемый результат: push не приходят.
5. Проверить deep link при нажатии на push из личного чата.  
   Ожидаемый результат: открывается нужный экран диалога.
6. Проверить quiet hours для маркетинговых уведомлений.  
   Ожидаемый результат: с 23:00 до 08:00 маркетинговые уведомления не отправляются.
7. Проверить доставку критичных уведомлений в quiet hours.  
   Ожидаемый результат: критичные уведомления приходят даже ночью.
8. Проверить поведение на Android и iOS.  
   Ожидаемый результат: уведомления обрабатываются корректно на обеих платформах.
9. Проверить переход через экран логина для разлогиненного пользователя.  
   Ожидаемый результат: после логина открывается целевой экран из push.

### Вывод

С применением grounding ответ стал заметно точнее: модель перестала опираться на общие представления о push-уведомлениях и начала учитывать конкретные требования задачи. Однако результат всё ещё остаётся относительно базовым: в нём уже есть нужные сценарии, но пока нет приоритизации, негативных кейсов и более глубокой проработки рисков.

**Итог:** grounding хорошо повышает **содержательную точность**, но сам по себе ещё не гарантирует удобный рабочий формат.

## 2. Few-shot

Few-shot задаёт модели образец ожидаемого результата. Благодаря этому улучшается единообразие структуры, формат ответа и уровень детализации.

### Без техники (before)

**Промпт:**  
Составь тестовые сценарии для push-уведомлений.

**Ответ модели:**
- Проверить получение уведомлений.
- Проверить открытие приложения по нажатию.
- Проверить отключение уведомлений.

### С техникой (after)

**Промпт:**  
Составь тестовые сценарии для push-уведомлений по аналогии с примерами.

Пример 1:  
Сценарий: Получение push при новом сообщении  
Шаги:
1. Отправить сообщение пользователю A от пользователя B.
2. Убедиться, что приложение пользователя A свернуто.  
   Ожидаемый результат: пользователь A получает push-уведомление с текстом сообщения.

Пример 2:  
Сценарий: Переход по push в экран чата  
Шаги:
1. Отправить пользователю push из личного чата.
2. Нажать на уведомление.  
   Ожидаемый результат: открывается экран нужного чата.

Теперь составь ещё 8 сценариев в таком же формате для фичи push-уведомлений в мобильном мессенджере.

**Ответ модели:**  
Сценарий: Получение push при упоминании в групповом чате  
Шаги:
1. Добавить пользователя в групповой чат.
2. Отправить сообщение с упоминанием пользователя.
3. Убедиться, что приложение свернуто.  
   Ожидаемый результат: приходит push с указанием упоминания в группе.

Сценарий: Отключение маркетинговых уведомлений  
Шаги:
1. Открыть настройки уведомлений.
2. Отключить маркетинговые уведомления.
3. Инициировать отправку маркетингового push.  
   Ожидаемый результат: маркетинговый push не приходит.

Сценарий: Отключение всех уведомлений  
Шаги:
1. Открыть настройки уведомлений.
2. Выключить все уведомления.
3. Отправить личное сообщение пользователю.  
   Ожидаемый результат: никакие push-уведомления не приходят.

Сценарий: Quiet hours для маркетинговых уведомлений  
Шаги:
1. Установить время 23:30.
2. Инициировать отправку маркетингового push.  
   Ожидаемый результат: маркетинговое уведомление не приходит.

Сценарий: Критичное уведомление в quiet hours  
Шаги:
1. Установить время 00:15.
2. Инициировать критичное уведомление.  
   Ожидаемый результат: критичное уведомление приходит, несмотря на quiet hours.

Сценарий: Переход на экран логина для разлогиненного пользователя  
Шаги:
1. Разлогинить пользователя.
2. Отправить push из личного чата.
3. Нажать на уведомление.  
   Ожидаемый результат: открывается экран логина, после успешного входа — целевой чат.

Сценарий: Проверка поведения на Android  
Шаги:
1. Установить приложение на Android-устройство.
2. Отправить пользователю личное сообщение.  
   Ожидаемый результат: push корректно отображается в системной шторке Android.

Сценарий: Проверка поведения на iOS  
Шаги:
1. Установить приложение на iPhone.
2. Отправить пользователю личное сообщение.  
   Ожидаемый результат: push корректно отображается в системных уведомлениях iOS.

### Вывод

Few-shot хорошо работает тогда, когда важно не только *что* ответит модель, но и *как именно* она это оформит. Примеры задали единый шаблон, и ответ стал значительно удобнее для использования.

При этом у техники есть ограничение: модель часто воспроизводит структуру примеров, но не всегда расширяет покрытие дальше них. Если примеры слишком простые, то и результат может остаться слишком простым.

**Итог:** few-shot лучше всего улучшает **формат, единообразие и ожидаемый уровень детализации**.

## 3. Role Prompting

Role prompting задаёт профессиональную оптику ответа. Модель начинает фокусироваться на тех аспектах, которые характерны для указанной экспертной роли.

### Без техники (before)

**Промпт:**  
Составь план тестирования для push-уведомлений.

**Ответ модели:**
- Проверить получение push.
- Проверить настройки уведомлений.
- Проверить открытие экранов.

### С техникой (after)

**Промпт:**  
Ты senior QA engineer в мобильной команде.  
У тебя опыт тестирования Android/iOS-приложений, deep links, notification payload и edge cases.  
Составь профессиональный план тестирования для фичи push-уведомлений в мобильном мессенджере.  
Сделай акцент на рисках, негативных сценариях и платформенных различиях.

**Ответ модели:**
- Проверка доставки push при разных типах событий: личные сообщения, групповые упоминания, критичные уведомления.
- Проверка корректности payload: title, body, deep link, тип уведомления.
- Негативные сценарии: отключённые разрешения, отсутствие сети в момент получения push, разлогиненный пользователь.
- Платформенные различия: Android notification channels, iOS permissions, фоновые ограничения.
- Проверка quiet hours и приоритетов уведомлений.
- Проверка перехода пользователя в нужный экран после авторизации.

### Вывод

Role prompting сделал ответ более профессиональным: появились риски, платформенные особенности и технические детали, которые часто важны именно для QA-специалиста.

Однако эта техника не заменяет конкретику. Если не задать требования, модель всё равно может остаться на уровне обзорного плана. Иными словами, роль помогает **сместить фокус**, но не подменяет собой полноценный контекст.

**Итог:** role prompting особенно полезен, когда нужен **экспертный угол зрения**, а не просто общий ответ.

## 4. Clarification

Clarification полезен в ситуациях, когда постановка задачи неполная или двусмысленная. Вместо того чтобы сразу выдавать потенциально неточный ответ, модель сначала помогает выявить недостающие требования.

### Без техники (before)

**Промпт:**  
Составь план тестирования push-уведомлений.

**Ответ модели:**
- Проверить получение уведомлений.
- Проверить отключение уведомлений.
- Проверить переход по нажатию.

### С техникой (after)

**Промпт:**  
Перед тем как составлять план тестирования, сначала задай уточняющие вопросы, которые нужны для качественного результата. После этого составь план на основе следующих предположений, если ответов нет:
- приложение — мобильный мессенджер;
- платформы — Android и iOS;
- есть личные, групповые, маркетинговые и критичные уведомления.

**Ответ модели:**  
Уточняющие вопросы:
1. Есть ли quiet hours и применяются ли они ко всем типам уведомлений или только к маркетинговым?
2. Что должно происходить при нажатии на push, если пользователь не авторизован?
3. Должны ли различаться сценарии для Android и iOS?
4. Есть ли настройка полного отключения всех уведомлений?
5. Нужно ли тестировать поведение при отключённых системных разрешениях на уведомления?

План тестирования на основе предположений:
1. Проверить получение push при новом личном сообщении.  
   Ожидаемый результат: уведомление приходит, содержит корректный текст и открывает нужный чат.
2. Проверить получение push при упоминании в групповом чате.  
   Ожидаемый результат: приходит уведомление с указанием факта упоминания.
3. Проверить отключение маркетинговых уведомлений.  
   Ожидаемый результат: маркетинговые push не приходят, остальные продолжают приходить.
4. Проверить отключение всех уведомлений.  
   Ожидаемый результат: ни один push не приходит.
5. Проверить quiet hours для маркетинговых уведомлений.  
   Ожидаемый результат: в quiet hours маркетинговые уведомления не доставляются.
6. Проверить критичные уведомления в quiet hours.  
   Ожидаемый результат: критичные push продолжают приходить.
7. Проверить переход по push для авторизованного пользователя.  
   Ожидаемый результат: открывается соответствующий экран.
8. Проверить переход по push для разлогиненного пользователя.  
   Ожидаемый результат: открывается экран логина, после входа — целевой экран.
9. Проверить базовое поведение уведомлений на Android и iOS.  
   Ожидаемый результат: уведомления корректно отображаются и обрабатываются на обеих платформах.
10. Проверить поведение при отключённых системных разрешениях.  
    Ожидаемый результат: push не отображается, приложение не падает, поведение соответствует системным ограничениям.

### Вывод

Clarification не столько “улучшает стиль ответа”, сколько повышает **зрелость самой постановки задачи**. Модель начинает работать не как генератор текста, а как помощник в уточнении требований.

Это особенно полезно в аналитике, тестировании и проектировании, где качество результата сильно зависит от полноты входных данных. Ограничение техники в том, что она удлиняет взаимодействие и не всегда нужна, если контекст уже достаточно хорошо описан.

**Итог:** clarification лучше всего помогает там, где есть **пробелы, двусмысленности и скрытые требования**.

## 5. Structured Prompting

Structured prompting задаёт чёткую архитектуру запроса: роль, контекст, задачу, формат ответа и ограничения. Благодаря этому результат становится более управляемым, предсказуемым и воспроизводимым.

### Без техники (before)

**Промпт:**  
Составь план тестирования для push-уведомлений в мобильном приложении.

**Ответ модели:**
- Проверить, что уведомления приходят.
- Проверить, что уведомления можно отключить.
- Проверить, что по нажатию открывается приложение.
- Проверить работу на разных устройствах.

### С техникой (after)

**Промпт:**  
Роль: ты senior QA engineer в мобильной команде.

Контекст:  
Есть мобильное приложение-мессенджер для Android и iOS.  
В приложении реализованы push-уведомления со следующими требованиями:
- push приходит при новом личном сообщении;
- push приходит при упоминании пользователя в групповом чате;
- пользователь может отключить маркетинговые уведомления;
- пользователь может отключить все уведомления;
- при нажатии на push должен открываться соответствующий экран;
- в quiet hours с 23:00 до 08:00 не должны приходить маркетинговые уведомления;
- критичные уведомления должны приходить даже в quiet hours;
- поведение должно корректно работать на Android и iOS;
- если пользователь разлогинен, нажатие на push должно открыть экран логина, а после логина — целевой экран.

Задача:  
Составь план тестирования этой фичи.

Формат ответа:  
Представь результат в виде таблицы с колонками:
1. ID
2. Сценарий
3. Шаги
4. Ожидаемый результат
5. Приоритет

Ограничения:
- не менее 10 сценариев;
- включи позитивные, негативные и edge-case сценарии;
- учти различия Android и iOS;
- учти настройки уведомлений, quiet hours, deep links и неавторизованного пользователя.

**Ответ модели:**

| ID | Сценарий | Шаги | Ожидаемый результат | Приоритет |
|---|---|---|---|---|
| TC-01 | Получение push при личном сообщении | 1. Отправить личное сообщение пользователю. 2. Свернуть приложение на устройстве получателя. | На устройство приходит push с корректным текстом сообщения. | High |
| TC-02 | Получение push при упоминании в групповом чате | 1. Отправить сообщение с упоминанием пользователя в группе. | Приходит push с указанием упоминания в групповом чате. | High |
| TC-03 | Отключение маркетинговых уведомлений | 1. Открыть настройки уведомлений. 2. Выключить маркетинговые push. 3. Отправить маркетинговое уведомление. | Маркетинговый push не приходит. | Medium |

### Вывод

Structured prompting дал наиболее управляемый результат. В ответе заранее определены роль, контекст, требования, формат и ограничения, поэтому итог ближе к рабочему тестовому артефакту, чем к общему рассуждению.

Кроме того, эта техника полезна для **воспроизводимости**: один и тот же хорошо структурированный запрос позволяет повторно получать ответы примерно одинакового качества и формата. Это особенно важно в реальных рабочих процессах.

При этом даже structured prompting зависит от качества входных данных: если требования неполные, то и результат будет структурированным, но не обязательно полным.

**Итог:** structured prompting даёт лучший баланс между **полнотой, предсказуемостью и практической пригодностью**.

## 📊 Сравнение техник

Ниже — краткое сравнение техник по тому, какой именно эффект они дают и где особенно полезны.

| **Техника** | **Что улучшает** | **Когда особенно полезна** | **Ограничение** |
|---|---|---|---|
| Grounding | Точность и привязку к требованиям | Когда важна бизнес-логика и предметный контекст | Не всегда задаёт удобный формат |
| Few-shot | Формат, единообразие, уровень детализации | Когда нужен ответ в конкретном шаблоне | Примеры могут ограничивать вариативность |
| Role Prompting | Профессиональный фокус и экспертную оптику | Когда важны риски, edge cases, технический взгляд | Не заменяет конкретные входные данные |
| Clarification | Полноту постановки задачи | Когда требования неполные или двусмысленные | Удлиняет взаимодействие |
| Structured Prompting | Управляемость, предсказуемость, воспроизводимость | Когда нужен почти готовый рабочий артефакт | Требует хорошо продуманного запроса |

Эта таблица показывает, что техники не дублируют друг друга полностью. Каждая из них улучшает результат по своему измерению.

## ⚠️ Дополнительные риски и edge cases

Если говорить о задаче тестирования push-уведомлений более профессионально, важно помнить, что даже хороший базовый план может не покрывать ряд существенных случаев.

### Примеры edge cases
- у пользователя отключены системные разрешения на push;
- устройство было офлайн в момент отправки уведомления;
- приложение находится в foreground, background или полностью выгружено;
- уведомление приходит с некорректным payload;
- пользователь нажимает на устаревший push, ведущий в уже недоступный объект;
- устройство находится в другом часовом поясе;
- на Android и iOS по-разному работает отображение и группировка уведомлений;
- возможны задержки доставки или дубликаты push;
- deep link может открываться некорректно после повторной авторизации.

Этот список важен потому, что показывает: качественный промпт помогает получить хороший стартовый результат, но **не заменяет профессиональную QA-аналитику**.

## 💡 Итоговый вывод

На примере задачи составления тест-плана для push-уведомлений видно, что разные техники промптинга улучшают ответ модели по разным направлениям.

- **Grounding** повышает содержательную точность и привязку к требованиям.
- **Few-shot** выравнивает формат и уровень детализации.
- **Role prompting** добавляет профессиональный фокус на рисках и платформенных особенностях.
- **Clarification** помогает выявить пробелы в постановке задачи.
- **Structured prompting** делает результат наиболее предсказуемым, управляемым и пригодным для практического использования.

Наиболее сильный результат в прикладных QA-задачах даёт **не одна техника сама по себе, а их комбинация**. На практике оптимальный подход может выглядеть так:

1. Сначала использовать **clarification**, чтобы выявить недостающие требования.
2. Затем добавить **grounding**, чтобы зафиксировать конкретный контекст и бизнес-логику.
3. После этого применить **role prompting**, чтобы направить ответ в сторону профессиональной экспертизы.
4. При необходимости использовать **few-shot**, чтобы задать желаемый формат тест-кейсов.
5. В конце оформить запрос через **structured prompting**, чтобы получить воспроизводимый и практически применимый результат.

Таким образом, техники промптинга стоит рассматривать не как набор независимых приёмов, а как инструменты, которые усиливают друг друга. Чем более прикладная и рабочая задача стоит перед моделью, тем выше ценность их осмысленного сочетания.
